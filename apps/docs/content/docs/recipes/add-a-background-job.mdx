<Callout type="info" title="Built for scheduled cleanup; not a job queue">
  This covers the shape that exists today — Vercel Cron, a shared wrapper, a
  plain idempotent function per job. For work that outlives a request (an
  export, a batch of emails), see "The shape for real jobs" below, which is
  not built yet.
</Callout>

## What exists: Vercel Cron on a shared wrapper

Every job is a route handler under `apps/web/src/app/api/jobs/<name>/`, kept
thin — it only re-exports `GET` from a same-named file in
`apps/web/src/jobs/`, which builds the handler with the one shared wrapper:

<include lang="ts" meta='title="apps/web/src/jobs/run-job.ts"'>../../../../../apps/web/src/jobs/run-job.ts#run</include>

The wrapper verifies the `Authorization: Bearer $CRON_SECRET` header,
answering 401 before anything else runs; logs the start and the outcome; caps
the batch a single call may touch at `MAX_JOB_BATCH_SIZE`; and reports a
thrown error to Sentry so a failure is an alert, not a silent 500.

`run` itself is a plain function with no knowledge of HTTP or the schedule —
`purgeStalePendingFiles()` in `apps/web/src/features/files/purge.ts` deletes
pending file rows whose upload window has passed, taking a limit and
returning how many rows it touched:

<include lang="ts" meta='title="apps/web/src/features/files/purge.ts"'>../../../../../apps/web/src/features/files/purge.ts#purge</include>

This is also why `audit_log` (see "Audit log" in ARCHITECTURE.md §10) has no
retention job of its own: a time-based delete and an append-only table are
mutually exclusive, and the audit log chose append-only.

Idempotent by construction: once every row past the cutoff is gone, the next
call's `WHERE` matches nothing. A backlog bigger than the batch cap clears
over several ticks of the schedule in `apps/web/vercel.json`, not in one call
that risks the function timeout.

Add a third job the same way: a plain function that takes a limit and
returns a count, a one-line file in `apps/web/src/jobs/` building the handler
with `createCronJobHandler`, a thin route re-exporting `GET`, and an entry in
`vercel.json`.

## The shape for real jobs

When a feature needs work that outlives a request — sending a batch of
emails, generating an export — the plan is:

- **A `jobs` table** (id, type, payload, status, attempts, `runAt`,
  `lockedAt`), so a job is a row and the queue is Postgres. No second
  infrastructure until there is a reason for one.
- **Enqueue from an action**, as step 4 of the mutation, inside the same
  transaction as the write it belongs to. A job for a record that was never
  saved cannot exist.
- **A worker route** on a cron schedule that claims rows with
  `FOR UPDATE SKIP LOCKED`, runs the handler for `type`, and records the
  outcome. Handlers are pure functions in `packages/jobs/src/handlers/`,
  tested without the worker.
- **Idempotent handlers.** A job may run twice; the handler must be safe to
  repeat.

## What to do in the meantime

Email already has its own answer: `sendEmail()` deferred with `after()` (see
[Add an email](./add-an-email)). For anything else, do the work inline in the action if it takes under a second; otherwise
record the intent as a row and leave a `TODO(jobs)` pointing here. Do not add
a queue library for one job.
